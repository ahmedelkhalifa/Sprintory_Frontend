# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — Vite dev server on http://localhost:5173 (must match the backend's `FRONTEND_URL`, or CORS/cookies fail)
- `npm run lint` — ESLint (flat config, `react-hooks` + `react-refresh` rules)
- `npm test` — unit tests for the pure helpers in `src/utils/` with Node's built-in runner (`node --test`, files in [tests/](tests/))
- `npm run build` — production build
- `npm run preview` — serve the built `dist/`

There are no component tests. CI ([.github/workflows/ci.yml](.github/workflows/ci.yml)) runs `npm ci`, `npm run lint`, `npm test`, `npm run build` on Node 24 for PRs and pushes to `main`; all must pass.

## Environment

Copy [.env.example](.env.example) to `.env` (gitignored):
- `VITE_API_URL` — backend base URL including the version prefix, e.g. `http://localhost:8080/api/v1`. API paths in code are relative to it (`/auth/register`).
- `VITE_SKIP_AUTH=true` (put it in `.env.local`) — TEMP dev bypass: `AuthProvider` skips `/auth/me` and uses a fake user so protected routes render without a backend.

## Stack

React 19 + Vite, plain JavaScript (`.jsx`, no TypeScript), MUI v9 with Emotion, React Router v7 (`BrowserRouter` / `<Routes>`, not the data router), axios.

## Architecture

**Backend contract.** The Spring backend (separate repo, `../sprintory_backend`, full docs in its `docs/`) owns every `/api/v1` contract. Frontend-focused summaries of the workspace, team, project, role, task and search contracts, plus a list of where the frontend is still behind them, are in [dev-docs/](dev-docs/) (start at [dev-docs/README.md](dev-docs/README.md)); read the relevant one before touching those API modules or pages, and update it when the backend doc changes. Auth: everything under `/api/v1/auth`, JSON in camelCase, errors shaped `{ status, code, message, path, fieldErrors? }`. Branch on `err.response.data.code` (`VALIDATION_ERROR`, `CONFLICT`, `PROVIDER_MISMATCH`, `INVALID_TOKEN`, `AUTHENTICATION_ERROR`, ...), never on `message`; messages are safe to display. `VALIDATION_ERROR` carries `fieldErrors` as `{ field: message }`, which maps straight onto form `errors` state.

**Auth is cookie-based.** Access and refresh tokens live in HttpOnly cookies set by the backend; the frontend never reads or stores tokens. Login state is known only through `GET /auth/me`.
- [src/api/client.js](src/api/client.js) — the single axios instance (`withCredentials: true`). Its response interceptor does a single-flight `POST /auth/refresh` on `401` with code `AUTHENTICATION_ERROR` and retries once; other 401s (e.g. `INVALID_TOKEN` from email links) pass through to the caller. Endpoints in `AUTH_PATHS` are never refreshed. On refresh failure it fires `AUTH_EXPIRED_EVENT` (except for `/auth/me`); `AuthProvider` clears the user and `ProtectedRoute` redirects, so the destination survives the login.
- [src/context/AuthProvider.jsx](src/context/AuthProvider.jsx) — calls `/auth/me` on mount and exposes `{ user, setUser, loading, logout }` through `useAuth()` ([AuthContext.js](src/context/AuthContext.js)).
- [src/components/general/ProtectedRoute.jsx](src/components/general/ProtectedRoute.jsx) — layout route in [App.jsx](src/App.jsx); everything nested under it requires a user and redirects to `/login` with `state.from`.

**Registration flow:** `/register` → `POST /auth/register` (no cookies, not logged in) → `/activate-account` ("check your inbox", email passed via router state) → user opens the emailed link `/verify-email?token=...` → `POST /auth/verify-email` once (guarded with a `useRef` because the token is single-use and StrictMode double-runs effects) → `/login` with `state.verified`. Re-registering an unverified email is how a user gets a new link; there is no resend endpoint. Google sign-in is a full-page navigation to `{backend origin}/oauth2/authorization/google`, outside `/api/v1`.

**Password reset:** `/reset-password` (linked from the login form) → `POST /auth/forgot-password`, which always answers `202` so the page never claims an email was sent → the emailed link opens `/reset-password?token=...` → `POST /auth/reset-password { token, newPassword }` → `/login` with `state.passwordReset`. `INVALID_TOKEN` means the link expired or was used.

**Invitations:** the emailed link opens the public `/accept-invite?token=...` ([AcceptInvitePage](src/pages/workspace/AcceptInvitePage.jsx)) → `POST /invitations/lookup` (no login) shows the workspace and invited email → signed in with that email: "Join workspace" → `POST /invitations/accept` → the workspace. Signed out: the token is kept in localStorage ([utils/invitation.js](src/utils/invitation.js)) and the user goes to login / register with the email prefilled; `ProtectedRoute` sends them back to the page once logged in (this also covers register → verify → login and Google). Signed in with another email: offer to sign out.

**Workspaces.** Roles are per workspace (`WORKSPACE_ADMIN` / `WORKSPACE_MEMBER`, read from the workspace response's `role`); an archived workspace (`archivedAt` set) is read-only. Workspace pages live under `/workspaces/:workspaceSlug/...`: browser urls use the workspace's `slug` (never changes, even on rename), API calls always the numeric `id`. Build links with `workspacePath(workspace)` / `projectsPath(workspace)` / `projectPath(workspace, project)` / `taskPath(workspace, project, taskId)`, never by hand; a project response only has `workspaceId`, so take the workspace from `useWorkspaceAccess()`.
- [src/components/general/ResourceAccessGuard.jsx](src/components/general/ResourceAccessGuard.jsx) — layout routes in [App.jsx](src/App.jsx): `WorkspaceAccessGuard` wraps every `/workspaces/:workspaceSlug/...` page and `ProjectAccessGuard` (nested inside it) every `.../projects/:projectId/...` page. The workspace guard finds the slug's id in the provider's list (`findWorkspace`; a slug not in it is not found, and an old `/workspaces/<id>` link redirects to the slug). They load the workspace / project first and show not found (404, also for invalid ids), a retry, or redirect a project opened under the wrong workspace; a page only renders once it's loaded and remounts when the id changes. Pages don't fetch it themselves: they read `{ workspace, reloadWorkspace }` / `{ project, reloadProject }` with `useWorkspaceAccess()` / `useProjectAccess()` from [hooks/useResourceAccess.js](src/hooks/useResourceAccess.js) and call the reload after a change. A new page under a workspace or project goes inside these routes.
- [src/context/WorkspaceProvider.jsx](src/context/WorkspaceProvider.jsx) — wraps `AppShell`; loads `GET /workspaces` and exposes `{ workspaces, loading, refreshing, error, reload, current }` through `useWorkspaces()` ([WorkspaceContext.js](src/context/WorkspaceContext.js)). The current workspace is the one in the url, else the last one opened (its id in localStorage). Sidebar links to workspace pages (e.g. Teams) are built from `current`. `refreshing` is true while the list reloads, so the guard waits instead of calling a just-created workspace's slug unknown.
- Mutations in [workspacesApi.js](src/api/workspacesApi.js) dispatch `WORKSPACES_CHANGED` and the provider reloads the list, so pages don't patch it by hand.
- Helpers: [utils/workspace.js](src/utils/workspace.js) (`isWorkspaceAdmin`, `isWorkspaceArchived`, `workspacePath`, `findWorkspace`, `parseWorkspaceId`, `ROLE_LABEL`), [utils/people.js](src/utils/people.js) (`initials`, `memberLabel`), [utils/page.js](src/utils/page.js) (`EMPTY_PAGE` for paginated lists).

**Projects.** Pages at `/workspaces/:workspaceSlug/projects` and `/workspaces/:workspaceSlug/projects/:projectId` (`/projects` redirects to the current workspace's list). Each project tab is its own child route (`.../:projectId` = Overview, `/members`, `/backlog`, `/board`, `/settings`, ...; ids in [tabList.js](src/components/projects/overview/tabList.js), urls from `projectTabPath`). [ProjectPage](src/pages/projects/ProjectPage.jsx) is their layout route: header, tabs and dialogs stay mounted and only the `<Outlet />` changes. The tab routes in [ProjectTabPages.jsx](src/pages/projects/ProjectTabPages.jsx) read what the layout shares (permissions, member preview, `openDialog`, `afterChange`, `goToTab`) with `useProjectPage()`. A new tab needs an entry in tabList.js and a route in App.jsx; unknown or Scrum-only tabs in Kanban redirect to Overview. Show or hide controls with `can(project, permission)` from [utils/project.js](src/utils/project.js), using the caller's `permissions` on the project response, never role names; the same file has `projectRoleLabel` (MEMBER is "Developer" in Scrum), `projectPath` and `suggestProjectKey`. Creating takes name, key (2–10 letters/digits, unique in the workspace, `409 PROJECT_KEY_TAKEN`), template and an optional description; key and template never change, and editing (`PATCH`, `EDIT_SETTINGS`) covers name and description only. It happens in the Settings tab ([ProjectSettingsTab](src/components/projects/ProjectSettingsTab.jsx), inline) or the header's Edit project window; both use `useProjectForm` and `ProjectFormFields`. The tab also has archive / restore / delete, with the same rules as the menus (`projectActionsFor`). Archive / restore / delete and project `status` / `createdAt` are built against **assumed** endpoints listed in [dev-docs/projects.md](dev-docs/projects.md). The project pages use the hooks in [src/hooks/](src/hooks/): `useAsync` (load one thing), `usePagedList` (searchable PageResponse list) and `useSubmit` (a change plus its error text). Each passes an `AbortSignal` to the API call.

**Tasks, board, backlog and sprints.** Tasks ([tasksApi.js](src/api/tasksApi.js)) and the board (`getBoard` in projectsApi) are real; sprints are not in the backend yet, so [sprintsApi.js](src/api/sprintsApi.js) uses the in-browser mock [src/mocks/sprintsMock.js](src/mocks/sprintsMock.js) unless `VITE_MOCK_SPRINTS=false` (localStorage, real project permissions). Summary and the **assumed** sprint contract in [dev-docs/tasks.md](dev-docs/tasks.md). A task's status is a board column (`statusId`); "done" is the last column (assumed). The Scrum-only Backlog tab is in [src/components/backlog/](src/components/backlog/), the Board tab (Scrum: active sprint + Complete sprint; Kanban: all tasks, WIP limits; columns read-only) in [src/components/board/](src/components/board/), and what both share (`TaskDrawer`, `QuickAddTask`, `CreateTaskDialog`, the `AssigneePicker` / `TaskValueSelect` fields, `loadWork`, dnd ids) in [src/components/tasks/](src/components/tasks/). `CreateTaskDialog` opens from the project header's Quick actions on any tab; the page then bumps `taskVersion` (useProjectPage) and an open Backlog / Board tab reloads. Each tab owns its data, drags with `@dnd-kit` and applies moves optimistically. Values in [constants/tasks.js](src/constants/tasks.js); pure helpers in [utils/task.js](src/utils/task.js) (`backlogView`, `moveInBacklog`, `taskChanges`, `describeTasks`, `movePermission`, ...) and [utils/board.js](src/utils/board.js). Moves use the backend's `afterTaskId` (null = first). Permissions: ranking the backlog `MANAGE_BACKLOG`, anything with a sprint `MANAGE_SPRINTS`, task edits and every board move `EDIT_TASKS`. `/workspaces/:workspaceSlug/projects/:projectId/tasks/:taskId` is a placeholder for the task page.

**Search.** The top bar's [GlobalSearch](src/components/search/GlobalSearch.jsx) calls `GET /search` ([searchApi.js](src/api/searchApi.js)) from 2 characters after a 300 ms pause and shows the hits grouped by kind; Enter or "See all results" opens `/search?q=&workspaceId=|projectId=&type=&page=` ([SearchPage](src/pages/search/SearchPage.jsx), all state in the url, outside the workspace guard). Ctrl/⌘+K or "/" focuses it. The scope ([useSearchScope](src/hooks/useSearchScope.js)) is the current workspace by default, with All workspaces / This project as chips at the top of the dropdown ([ScopeMenu](src/components/search/ScopeMenu.jsx) on the results page). On phones the top-bar field is a search button that opens over the whole bar. Build a hit's route with `searchResultPath` from [utils/search.js](src/utils/search.js), never from the response's `path` (an API path); a team hit opens `.../teams?team=<id>`, which TeamsPage selects. Tasks only come from projects the user is in, even for a workspace admin. Summary in [dev-docs/search.md](dev-docs/search.md).

**Roles.** Workspace roles are changed on the Members page (`/workspaces/:workspaceSlug/members`, [WorkspaceMembersPage](src/pages/workspace/WorkspaceMembersPage.jsx)): admins get a dropdown per row, everyone else a label. Project roles are changed in [ProjectRolesDialog](src/components/projects/ProjectRolesDialog.jsx), opened from the Members tab for people with `MANAGE_ROLES`; the role lists per template and the toggle / validation helpers are in [constants/projects.js](src/constants/projects.js) and [utils/project.js](src/utils/project.js). Details in [dev-docs/roles.md](dev-docs/roles.md).

**API modules.** One file per backend area in [src/api/](src/api/), named `<area>Api.js` (`authApi`, `workspacesApi`, `teamsApi`, `projectsApi`, `tasksApi`, `sprintsApi`, `searchApi`), each importing the shared `api` client and returning `res.data`. Don't redefine an endpoint in another area's file. List/get functions take an optional `AbortSignal` last; effects pass one and abort in their cleanup so a stale response never lands. For error text outside the auth forms use `errorMessage(err, fallback, overrides?)` (overrides are a page's own texts by code) / `isAbort(err)` from [utils/apiError.js](src/utils/apiError.js).

**Pages vs. components.** `src/pages/<area>/` holds route-level components that compose a layout and a card/form, e.g. `RegisterPage` = `AuthLayout` → `AuthCard` → `RegisterForm`. Form logic and page pieces live in `src/components/<area>/` (`auth`, `projects`, `teams`, `workspace`; shared pieces like `LoadState`, `Pager`, `ConfirmDialog` in `general`); reusable inputs (`FormField`, `PasswordField`) in `src/components/forms/`. Validation helpers in [src/utils/validation.js](src/utils/validation.js) return `{ field: message }` with only the invalid fields, so the same object works for both client and server errors.

**Styling.** Use MUI components with `sx` and theme tokens from [src/theme/theme.js](src/theme/theme.js) (custom palette keys `navActive`, `ai`, `topBar`, `avatar`; buttons are not uppercased). There is a light and a dark palette (`createAppTheme(mode)`), chosen on the Settings page ([AppearanceSettings](src/components/settings/AppearanceSettings.jsx): Light / Dark / System) and applied by [ColorModeProvider](src/context/ColorModeProvider.jsx) (`useColorMode()`, kept in localStorage; the auth pages always use `lightTheme`). So never hard-code colors: no hex, no `"white"`; `primary.dark` is only a hover / dark fill, so use `navActive.text` for strong blue text and `topBar.background` for the navy bar. For short viewports use the `SHORT_SCREEN` media-query key from [src/theme/media.js](src/theme/media.js) inside `sx`. `AuthLayout` is exactly one screen tall; only the form column scrolls.

## Conventions

- Functional components as `const X = () => {}` with `export default X`, 2-space indent, double quotes, semicolons.
- MUI: use `slotProps` (`slotProps={{ input: ... }}`, `slotProps={{ paper: ... }}`), not the deprecated `InputProps` / `PaperProps` / `inputProps` / `primaryTypographyProps`.
- Short lowercase comments explaining *why*.
- Git: feature branches named like `pages/register-page`, `setup/skeleton-app`; PRs into `main`.
